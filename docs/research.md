此前 v0.6 的“设计稿／暂不开放”描述已成为历史：R025–R032 全部实现，最高骰核心已改为优势转换；见 [当前设计](design80.md)。下面保留原研究的出处和当时取舍，勿把历史实现状态当作当前状态。

## 新增：幸运房东（LBL）

[官方商品说明](https://store.steampowered.com/app/1404850/Luck_be_a_Landlord/) 明确符号具有不同效果和交互，物品组合形成构筑。由此得到的本项目分析是：经济收益应与触发条件和消费出口连接。R010 奇数产金 → R065 消费银行，或 R078 直接消耗回合金币换下回合优势已实现。上限12、银行3和5个辅助槽是我们的平衡决策，不冒充原作采用的具体方案。尚未找到足以归因某项开发困难及其解法的一手复盘，因此不虚构幸运房东的开发经历。

# 参考研究：把骰子随机变成可理解的选择

检索日期：2026-11-09。范围是 Balatro、Pip My Dice、Slice & Dice、Dicey Dungeons、Die in the Dungeon。本文研究机制关系与开发方法，不复刻原作卡名、卡文、美术或完整内容库。数据库的 `reference_ids` 表示机制启发来源，**不是原作存在同名技能的声明**。

## 如何读这份报告

- **已核实机制**：来自开发者、发行页面或官方说明。
- **开发者陈述**：开发日志、开发者本人回顾或直接采访。记录其经验，不把一次处理措施写成永远解决了所有问题。
- **设计分析**：我们依据机制判断的风险，不冒充原作者遇到过的具体事件。
- **本项目决策**：再见一掷自己的选择，是否生效由实现和试玩验证。

## 开发困境、玩法困境与已知应对

### Balatro

**开发者陈述：** LocalThunk 说明发行后的平衡更新和移动移植连续消耗精力，之后通过休息、降低工作强度和放弃硬性更新期限调整节奏。[B2] 这属于开发可持续性问题，不是某个卡牌算法的技术解法。

**玩法与应对：** 他解释挑战、解锁等长期目标的一项作用，是促使玩家离开惯用策略、探索系统。[B3] 官方 FAQ 则确认不同 Joker 影响计分、牌张和经济。[B1]

**我们的取舍：** 先保证少量流派能改变锁骰决策，再扩展卡数；R025–R032 不因“数据库里有名字”就开放。设 5 被动 + 1 核心，使拿新卡需要考虑取代谁。后续挑战可要求不使用逆点、限定经济卡等，但本版不做永久数值成长。

### Pip My Dice

**开发者陈述：** Fokaz 在复盘中说早期画面较粗糙，试玩帮助发现便利性缺口和错误；观看主播录像进一步暴露 UX 问题。控制器、本地化等收尾工作也导致排期延后。[P2]

**已核实机制：** 游戏提供骰面改造、遗物联动与组合槽成长来扩大构筑空间。[P1] 这证明“玩家可以改变概率”，但不能据此声称它彻底消除了随机挫败。

**我们的分析与取舍：** 三枚骰子如果只看总和，会很快收敛成“保留大点”。对子、顺子、奇偶和逆点各自奖励不同保留策略；商店和休息点让经济有用途。保留种子、结算输入和逐条结果，先用可复现案例修错误，再通过玩家录像判断界面是否清楚。骰面深度改造暂只保留校准第一枚骰子，复杂改造作为后续项。

### Slice & Dice

**已核实机制：** 官方页面说明可选择重掷骰子，并支持撤销行动。[S1] **开发日志证据：** 1.0.3 加入错误报告、调整关键词可用位置以改善清晰度；3.1 增加字体与掷骰速度选项，并持续调整内容。[S2][S3]

这些日志证明团队在改善诊断、阅读和节奏，**不证明所有改动来自同一种失败原因，也不证明开发者采用了我们这里的状态架构**。

**我们的取舍：** 锁定操作在下一掷前可反悔；随机结果揭晓后不提供“撤销重掷再试运气”。预览与正式结算调用同一纯函数。动画只展示结果，不能重复发奖或改骰面。逐条高亮、结算轨迹和导出诊断已实现；动画倍速列入下一轮交互验收后再做。

### Dicey Dungeons

**开发者采访：** 女巫原型曾出现骰子无处使用、自动法术同时触发难以理解、初始法术太齐全而使拾取缺乏吸引力等问题。开发者转向可规划的召唤装备，给剩余骰子用途，引入骰子操作，并减少初始法术、提高后续拾取吸引力。[D1]

**我们的取舍：** 每枚骰子默认都计入基础总和；不因没有凑出组合就完全作废。开局不塞满永久规则。触发分成明确阶段而非同时闪屏。低点用途和有限防护提供退路，但不保证每次低掷都有收益。基础与条件收益保持分开，玩家能理解“没有组合”和“完全没行动”之间的区别。

### Die in the Dungeon

**开发者 AMA：** 团队称棋盘实现从简单版本迭代而来，使用二维数组与若干计算遍历；多系统交互让难度平衡很难，抢先体验反馈促成调整。团队也删减过区域与敌人设想来控制规模。[I2]

**尚未解决的例子：** 同一 AMA 中，开发者承认“棋盘上直接查看骰子全部信息”的功能受屏幕空间影响，当时仍未完成。[I2] 因此不能把它写成原作已经解决的案例。

**我们的取舍：** 只保留三枚玩家骰子，不移植其空间棋盘。使用原始骰面 → 结算副本 → 计分 → 胜负 → 伤害的明确计算阶段。图鉴与原型读取同一数据库，减少卡文和代码不一致。牌位复制、跨回合借贷等容易增加交互组合的机制暂不开放。

## 再见一掷自己的问题与落地解法

| 困境 | 本项目解法 | 状态 / 验证 |
|---|---|---|
| 总是保留 4–6，锁骰没有流派差异 | 不同点数组合、首掷持续锁定和末掷数量条件 | 已实现，逐卡测试；还需观察玩家策略是否变化 |
| 加分牌与低点获胜互相抵消 | 统一“优势”：正常加分、逆点减分，最低 0；敌人按模式锁骰 | 已实现，逆点与封底测试 |
| 单骰加全套加分，形成稳定压制 | 单骰核心跳过双方计分；最高骰相同改比原始总和 | 已实现，避免镜像必平；伤害/经济牌仍可构筑 |
| 规则越拿越多，选择退化为全都要 | 5 个被动位 + 1 个核心位；替换同类位置或跳过拿金币 | 已实现；付费替换取消不会扣钱 |
| 连锁一闪而过，看不懂结果 | 第三掷完整预览，逐来源日志，触发牌高亮 | 已实现；真实浏览器视觉验收仍待完成 |
| 反复拖回合刷钱 | 奇数金币每场最多 9，击杀金币一次，成长最多 3 | 已实现，有封顶和重置测试 |
| 大 Boss 仅靠骰数碾压常规流派 | 首章 Boss 改三骰、36 生命、半血每偶数 1 优势 | 已实现，仅为测试起点；不是最终平衡结论 |
| 扩展卡牌造成重复逻辑和陈旧文本 | JSON 唯一编辑源、生成 HTML/CSV/图鉴、CI 检查一致性 | 已实现 |
| 设计稿被误当成成品 | 明确 implemented / planned，奖励只读前者 | 已实现，测试阻止未实现卡装备 |

## 下一步的验证顺序

1. 让新玩家在第一场战斗后解释锁定、三掷、差值伤害；记录哪里需要口头提示。
2. 给同一个玩家奇偶、对子、逆点三组规则，观察保留哪些骰子是否改变。
3. 让玩家不读日志预测第三掷结算，然后对照预览，找出语义模糊的卡。
4. 全路线试玩，而非仅把成型构筑直接塞进 Boss 战；统计获得顺序、残血与商店支出。
5. 如果逆点仍明显支配其他流派，先调整条件与获取时机，再考虑改倍率；不让首领免疫直接废掉整套构筑。
